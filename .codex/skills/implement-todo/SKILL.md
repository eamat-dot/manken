# Implement TODO

リポジトリ内の実装TODOを、作業記録かつ完了判定の基準として扱う。実装TODOには、必ず「TODO準備 → 実装計画 → 実装・検証・完了処理」の順で取り組む。

## 1. 作業前の確認

1. リポジトリの `AGENTS.md` と、変更対象に適用される指示書を読む。
2. `docs/todo/` を扱う場合は、必ず `.github/instructions/todo.instructions.md` を読む。ここにTODO番号、書式、配置、チェック欄、完了判定の正本がある。
3. ユーザーが既存TODOを指定した場合は、そのファイル、`docs/todo/000-template.md`、関連する仕様書、コード、テストを読む。
4. TODOが指定されていない場合は、`000-template.md` を読み、未使用の次番号でTODOを作成する。`docs/todo/`、`done/`、`pending/`、`archived/` を確認し、使用済み番号を再利用しない。

テンプレートはこのスキルへ複製しない。常に対象リポジトリにある現行の `000-template.md` を使う。

## 2. TODOを実装可能な状態にする

コードを変更する前に、TODOを現行テンプレートと実態に照らして確認する。

- 目的、非目的、対象範囲、前提・制約、実施項目、検証、受け入れ条件を確認する。
- 既存TODOの不足、矛盾、すでに完了済みの項目、実態と異なる前提を修正する。
- 実施項目、検証、受け入れ条件を、確認可能なチェックリストにする。
- 調査で不要になった項目は、理由を残して削除または置き換える。実施せずにチェックしない。
- 実装開始を妨げる未決事項や、目的を大きく変える判断がある場合は、実装せずに状況と選択肢をユーザーへ報告する。

TODO本文と同じ作業内容を、別の恒久的な `plan.md` などに重複して作成しない。

## 3. 実装計画を作る

TODOが実装可能な状態になった後、ソースコードの変更前に、Codexの実行プランを作成する。計画には、TODOの実施項目に対応する変更単位、変更対象と依存関係、テスト・文書更新・検証の順序を含める。

調査中または実装中に影響範囲が変わったら、計画だけでなくTODOの範囲と完了条件も更新する。

## 4. 実装、検証、進捗更新

計画に沿ってコード、テスト、仕様書、利用者向け文書を変更する。各チェック欄は、対応する作業と必要な確認が実際に完了した時点でのみ `[x]` に更新する。

- 成功した検証コマンドだけをチェックする。
- 未実行、実行不能、失敗、または部分完了の項目は未チェックのまま残す。
- 外部サービスや認証情報のために検証できない場合は、理由、確認済みの範囲、残作業をTODOへ記録する。
- 実施済みのコードとTODO、仕様書、利用者向け文書が矛盾しないことを確認する。

コミット、push、merge、ブランチ削除は、このスキルの作業に含めない。ユーザーが明示的に依頼した場合だけ行う。

## 5. 完了判定と移動

TODOの目的を満たし、実施項目、検証、受け入れ条件をすべて確認する。TODO本文に未完了の `- [ ]` が一つでもある、または完了を妨げる未決事項がある場合は、完了扱いにしない。

すべての完了条件を満たした場合だけ、同じファイル名のまま `docs/todo/done/` へ移動する。コピーを残さない。完了できない場合は、完了済み項目、未完了項目と理由、実行した検証結果、次の作業を報告し、TODOは進行中の場所に残す。
