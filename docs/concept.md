# mankenの設計方針

この文書は、`manken` が目指す役割と責務分担を整理する。
公開APIの現在の動作を定義する仕様書ではなく、実装または仕様書と食い違う場合は、
実装と仕様書を正としてこの文書を更新する。

## 目的

`manken` は、書籍・漫画・電子書籍に関する複数の外部サービスを、用途に応じて利用できる
Goライブラリを目指す。

各プロバイダの通信方式、認証、検索条件、レスポンス形式の違いをそれぞれのパッケージで扱い、
利用側が必要なプロバイダだけを選べる構成を維持する。
すべてのプロバイダへ同じ検索能力や同じ書誌項目を要求せず、書誌検索、ISBN参照、商品検索、
販売情報など、取得元ごとの得意な用途を活かす。

現在はMADB、openBD、Google Books、楽天Books、楽天Kobo、DMMブックス、Yahoo!ショッピング、NDLサーチの個別パッケージと、明示した一つの取得元へ委譲するルートファサードを提供する。ルートファサードは横断検索を提供せず、MCPサーバーは検索ライブラリ本体と分離する。

## 取得結果の扱い

取得元の情報は、共通化した情報とRaw responseを役割の異なる出力として扱う。

- 共通 `Book`
  - 複数の取得元で同じ意味として安全に扱える書誌情報を直下の共通フィールドで提供する
  - 通常のGoコードや、取得元をまたいで共通項目を扱う処理で利用する
  - 取得元タイトルは非破壊で保持し、取得元にない情報や意味を安全に判断できない情報を推測して補完しない
- Raw response
  - 取得元から受信したレスポンス本文を、取得元固有の詳細を確認するために利用する
  - 共通モデルでは表現しない項目や、変換前の値を必要とする用途で利用する
  - `Book` へ複製せず、取得元パッケージの専用メソッドでリクエスト単位に扱う
  - 取得元の成功本文に認証情報が含まれる場合は、取得元パッケージが秘匿してから返す

Raw responseを利用できることは、正規化を不要にする理由とはしない。
反対に、すべての取得元固有情報を共通 `Book` へ取り込むことも目的としない。
共通処理に適した情報は正規化し、取得元固有の情報はRaw responseに残す。

DMMブックスでは、keyword結果の代表商品を共通 `Book` へ変換しない。個別商品を共通 `Book` として扱う条件は、[DMMパッケージ仕様](pkg/dmm/spec.md) で定める。

## プロバイダの評価

新しいプロバイダは、共通書誌モデルへ変換できる項目数だけで採否を判断しない。
用途に応じて、少なくとも次の観点を分けて確認する。

- タイトル、著者名、ISBNなどによる書誌検索・参照
- 書誌情報の信頼性と、共通 `Book` へ安全に変換できる範囲
- 電子書籍や販売商品の検索
- 価格、販売状態、商品URL、画像などの商品・販売情報
- Raw responseに含まれる取得元固有情報の有用性
- APIの認証、利用条件、レート制限など、利用開始と継続利用に必要な条件

ある用途に弱いプロバイダでも、別の用途に有用であれば取得元候補として扱う。
たとえば、ISBNや巻数を安定して取得できない販売系APIを、書誌検索元として採用しない一方で、
電子書籍の商品検索や販売先の提示に利用することはあり得る。

取得時点価格は `Book.CurrentPrice`、通常商品URLとアフィリエイトURLは `BookSource` の別項目として
扱う。在庫、送料、レビューなど追加の販売情報は複数の販売系プロバイダを比較してから責務と
モデルを決める。アフィリエイトは利用例の一つとして扱い、`manken` 自体の主目的にはしない。

`BookSeries` は取得元が作品または個別Bookの系列として明示する値、`PublicationSeries` は叢書、刊行シリーズ、コミックレーベル、Publisher collection等の出版側グループ表示として分ける。文字列内容から両者を相互に推測設定しない。
取得元が独立した系列実体を明示しない出版側の表示へ、独自のIDやURLを生成して `BookSeries` として扱わない。

## 横断検索と照合

ルートファサードは、利用側が生成したprovider Clientを必要な分だけ登録し、呼び出しごとに明示した一つのSourceの既存操作へそのまま委譲する。複数providerを一回で検索する機能ではない。
すべての取得元が同じ検索条件やページングを提供するとは限らないため、複数取得元を組み合わせる処理は利用側の責務とする。

ISBNなど信頼性の高い識別子で確実に判断できる範囲はライブラリで機械的に扱える。
タイトル、著者名、巻数、版違いなどから同一書籍かを推測する処理は誤判定の可能性があるため、
推論を必要とする照合を共通ライブラリの必須責務にはしない。

## MCP / LLMとの境界

MCPサーバーは検索ライブラリ本体と分離した独立repository / Go moduleで実装し、
`manken` 本体をMCP SDKへ依存させない。MCP層は利用側としてルートファサードまたは
各providerの公開APIを呼び出す。

MCP / LLMからは用途に応じて、共通 `Book`、Raw response、またはその両方を利用できる形を
維持する。LLMがRaw responseを解析できる場合でも、共通項目を安定して扱える
`Book` の共通フィールドは引き続き有用な出力として維持する。

## 現在の責務分担

- 取得元ごとのパッケージが通信、認証、レスポンス解析、安全な共通モデルへの変換を担当する。Raw responseは各providerが公開する `...WithRawResponse` メソッドから直接取得できる
- ルート `manken` パッケージはprovider Clientを生成せず、対応する検索またはISBN参照roleへ一回だけ委譲する。ルートの `SearchBooksWithRawResponse` / `LookupBooksByISBNWithRawResponse` からも同じ経路を利用でき、provider由来の結果、Raw response、エラーは変更しない
- 取得元パッケージから別の取得元パッケージを内部で呼び出して補完やfallbackを行わない。
  暗黙の横断取得は、必要な認証情報、通信回数、エラー、順序、ページングの境界を不明確にするため、
  複数取得元の組み合わせは利用側で扱う
- ライブラリ本体は環境変数から認証情報を読み込まない。プロセス全体に暗黙の設定を持たず、
  利用する取得元の資格情報をClient設定として明示するためである
- 利用しないプロバイダの認証情報や設定を要求しない
- 欠落する書誌項目を正常な状態として扱う
- 取得元にない情報や意味を推測で補完しない。取得元タイトルからは、共通仕様で安全と定めた巻表示、
  版表示、完結表示だけを補助フィールドへ抽出できる
- 現行ライブラリはリトライ、キャッシュ、内部レート制御、ログ、並行実行を提供しない。
  取得元ごとに利用条件が異なり、暗黙に追加すると通信回数、待機時間、データ鮮度が
  呼び出し側から見えなくなるため、必要な場合は呼び出し側が制御する
- 取得元の実データを確認してから、共通化できる項目、検索条件、商品・販売情報の扱いを決める
