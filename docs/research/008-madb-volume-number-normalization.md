# MADB巻数表記の調査記録

## 1. 調査目的

MADBの `schema:volumeNumber` に格納されている実データを分類し、元表記を
`api.Book.VolumeNumber` に残したまま、並べ替えに使用できる値を安全に
取り出せる範囲を確認する。

この文書は2026年7月30日時点の調査記録であり、確定仕様ではない。
規則案は承認後に仕様書へ反映する。

## 2. 調査方法

MADBの公式SPARQLエンドポイントへPOSTし、`class:MangaBook` が持つ
`schema:volumeNumber` を値ごとに集計した。

```sparql
PREFIX schema: <https://schema.org/>
PREFIX class: <https://mediaarts-db.artmuseums.go.jp/data/class#>

SELECT
  ?volumeNumber
  (COUNT(DISTINCT ?resource) AS ?count)
  (MIN(STR(?resource)) AS ?representative)
WHERE {
  ?resource a class:MangaBook ;
            schema:volumeNumber ?volumeNumber .
}
GROUP BY ?volumeNumber
ORDER BY ?volumeNumber
```

別の集計クエリで、マンガ単行本の総数と巻数を持つマンガ単行本数を確認した。
集計結果はサービスの更新によって変化する。

| 項目 | 件数 |
| --- | ---: |
| マンガ単行本 | 401,311 |
| 巻数を持つマンガ単行本 | 286,298 |
| 巻数を持たないマンガ単行本 | 115,013 |
| 異なる巻数表記 | 9,463 |

巻数を持つマンガ単行本は全体の約71.3%であった。値ごとの件数の合計も
286,298件であり、今回の取得結果では1冊に異なる巻数値が複数設定された例は
なかった。空文字列と、前後に空白を持つ値もなかった。

## 4. 数字が複数ある値

数字列の数を、全角数字を半角数字へ置き換えた後に数えた。

| 数字列の数 | 異なる表記 | 冊数 |
| ---: | ---: | ---: |
| 0 | 2,745 | 10,051 |
| 1 | 5,875 | 274,961 |
| 2 | 786 | 1,226 |
| 3 | 53 | 55 |
| 4 | 3 | 4 |
| 8 | 1 | 1 |

複数の数字が同じ値でも、次の違いがある。

- `2　／　第2巻` は同じ巻数の別表記を併記している
- `1　／　01` は先頭ゼロを無視すれば同じ数になる
- `1.5` は小数であり、`1`と`5`の併記ではない
- `1-2` は範囲または枝番の可能性がある
- `no. 3 (2016)` は巻数と年を含む
- `2 (V3大かつやく!!の巻)` は巻数らしい数字と説明中の数字を含む

文字列から最初の数字だけを取り出す方法では、これらを区別できない。

## 5. Unicodeと空白

全値へNFKCを適用すると、631種類、1,303冊の表記が変化した。

| 元表記 | NFKC適用後 |
| --- | --- |
| `１` | `1` |
| `＃1` | `#1` |
| `2　／　第2巻` | `2 / 第2巻` |
| `Ⅱ` | `II` |

NFKCは数字と区切りだけでなくローマ数字も展開する。巻数文字列全体には適用せず、
解析時に次の文字だけを対象として置き換える方が安全である。

- 全角数字`０`から`９`をASCII数字へ置き換える
- `卷`を`巻`と同じ接尾辞として判定する
- 全角の`＃`と`／`を、対応する接頭辞または区切りとして判定する
- ASCII空白と全角空白は、許可した構文の構成要素間だけ無視する

元の `VolumeNumber` には、これらの置き換えを適用しない。

## 6. 規則案

### 6.1 共通方針

- 元表記は現在の `VolumeNumber` に変更せず保持する
- 文字列全体が許可した構文に一致する場合だけ、比較用の値を作る
- 説明文の一部から数字を抽出しない
- 複数の表記を併記している場合は、各要素を独立に解析し、すべて同値の場合だけ
  比較用の値を作る
- 数字が競合する値、範囲、複数巻収録、年月、号は比較用の値を作らない
- 解析できない値はエラーにせず、元表記だけを返す

### 6.2 初期対象の推奨

次の表記は、数値部分を10進数の文字列へ変換する候補とする。

- ASCII数字と全角数字だけの値
- `第N巻`、`第N卷`、`N巻`、`N卷`
- `v.N`、`vol.N`、`volume N`と、大文字小文字や空白の違い
- `no.N`、`#N`、`＃N`
- `[N]`、`［N］`、`(N)`、`（N）`
- 許可済みの表記を区切りで併記し、すべてが同じ数になる値

次の表記は初期対象に含めないことを推奨する。

- 漢数字とローマ数字
- `集`、`部`、`part`
- 上巻、中巻、下巻、前編、後編
- 小数、枝番、範囲、複数巻収録
- 別巻、外伝、番外編、総集編
- 年月、季節、号を含む値
- 許可した構文以外の説明を含む値

漢数字、小数、上下巻などを後から追加できるようにするが、初期規則では
変換範囲を広げない。特に小数は `float64` にせず、追加時も元の桁を失わない
10進数文字列として扱う。

## 7. モデル案

### 案A: 共通`Book`へ`NormalizedVolume`を追加

- 利点: 利用側が正規化済みの表示値を直接使用できる
- 欠点: 比較順を表すのか表示用文字列を表すのかが名称から分からない
- 影響: 公開Go APIとJSONへ項目が増え、規則変更が互換性へ影響する

### 案B: 共通`Book`へ`VolumeIndex`または`VolumeOrder`を追加

- 利点: 巻数順の比較に使う値であることを示しやすい
- 欠点: 単一の整数や文字列では、上下巻、小数、別巻、範囲を表せない
- 影響: MADB以外の取得元で同じ意味を持つか、まだ確認できていない

### 案C: MADB内部の比較キーにする

- 利点: 公開APIと元表記を変えず、実データに合わせて規則を改良できる
- 欠点: 利用側へ正規化値を返せず、他の取得元と処理を共有できない
- 影響: 検索結果の並べ替えを実装するとき、カーソルにも同じキーを含める必要がある

初期実装では案Cを推奨する。現時点で調査済みの取得元はMADBだけであり、
共通モデルには複数の取得元で意味が一致すると確認できた概念だけを追加するという
既存方針に合うためである。

内部名は、表示値ではなく比較専用であることを示す `volumeSortKey` を候補とする。
型は単一の整数や浮動小数点数ではなく、解析できた種類と10進数文字列を持つ
非公開の構造体とする。正確なフィールドと比較順は、検索結果の並べ替えを設計する
TODO009で確定する。
