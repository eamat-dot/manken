# プロバイダごとの検索・取得能力を整理する

## 背景

- 現状:
  - TODO026で、`manken` は正規化だけでなく複数の書籍・電子書籍・販売系プロバイダを用途に応じて利用するハブを目指す方針へ整理した
  - MADB、openBDは実装済みで、DMM.com Webサービスは実APIを含む調査済み
  - Google Books、楽天Books、楽天Kobo、Yahoo!ショッピングは既存の比較調査やサンプルがあるが、実装状態と確認水準が異なる
- 課題:
  - プロバイダごとに検索条件、対象データ、識別子、販売情報、Raw responseなどの能力が異なる
  - capabilityをGoの型やインターフェースとして設計する前に、比較に使う評価軸と確認水準を揃える必要がある
  - 古い調査結果、公式仕様だけの確認、実レスポンス確認、実装済み動作を同じ確度として扱うと、横断検索やMCP設計を誤りやすい
- 変更が必要な理由:
  - 今後のプロバイダ調査を同じ基準で進め、横断検索・販売情報・MCPの設計判断に再利用できる比較資料を作るため

## 目的

- このTODOで達成すること:
  - プロバイダの検索・取得能力を比較する共通の評価軸を定義する
  - MADB、openBD、DMM.com Webサービスについて、現在確認済みの能力を整理する
  - Google Books、楽天Books、楽天Kobo、Yahoo!ショッピングについて、既存調査で確認済みの範囲と再確認が必要な範囲を区別して整理する
  - 今後の個別プロバイダ調査で使える確認項目を標準化する
- 期待する利用者視点の結果:
  - どのプロバイダをどの用途に使えるかを、正規化できる項目数だけでなく検索・商品・販売・Raw responseなどの観点から比較できる
  - 将来の横断検索やMCPで、どの能力を共通化できるか判断する根拠が残る

## 非目的

- 今回は扱わないこと:
  - capabilityを表すGoインターフェース、構造体、列挙型の設計・実装
  - 横断検索APIの設計・実装
  - 販売情報・アフィリエイト情報の共通モデル設計
  - MCPツールSchemaの確定
  - 未実装プロバイダの新規API実装
  - 既存調査にない外部APIを推測で評価すること
- 別Issueや別TODOで扱うこと:
  - Google Books、楽天Books、楽天Kobo、Yahoo!ショッピングの現行API・実レスポンス再確認
  - capabilityを公開APIで表現する必要があるかの設計判断
  - 販売情報モデルと横断検索の具体設計

## 前提・制約

- 変更してよい範囲:
  - `docs/research/027-provider-capabilities.md`
  - `docs/backlog.md`
  - 必要な場合の `docs/concept.md`、`docs/idea.md` の軽微な整合調整
  - TODO027本文
- 変更してはいけない範囲:
  - Goコードと公開API
  - 現在の実装動作を表す `docs/spec.md` と取得元パッケージ仕様を、未実装能力が存在するように変更しない
  - 過去の調査結果を、現在も確認済みであるかのように書き換えない
- 互換性要件:
  - 現行の `NormalizedBook`、Raw response、検索・ISBN参照APIの仕様を変更しない
- パフォーマンス要件:
  - 文書調査のみのため該当なし

## 想定ユースケース

- 入力:
  - 新しいプロバイダ候補、または既存プロバイダの仕様・実レスポンス
- 実行:
  - 共通の評価軸で、提供できる検索・参照・商品・販売・Raw responseの能力と確認水準を記録する
- 出力:
  - プロバイダ比較表と、用途別の選択指針
  - 後続調査で確認すべき標準チェック項目
- 失敗時の扱い:
  - 公式仕様や実レスポンスで確認できていない能力は「未確認」または「再確認必要」とし、推測で○にしない

## 処理方針

1. 実装済み仕様と既存researchを確認し、評価軸を定義する
2. 各プロバイダについて、実装済み・実レスポンス確認済み・仕様確認のみ・未確認を区別して表にする
3. 「書誌検索向け」「ISBN参照向け」「商品・販売検索向け」「MCP / Raw利用向け」の用途別評価を整理する
4. 今後の個別調査で再利用するチェックリストを作る
5. backlogから今回完了した抽象的な整理項目を除き、具体的な再調査・設計作業だけを残す

## リスク・懸念

- 2026-07-30前後の既存調査は現在の外部API仕様と差が生じている可能性がある
- 「API仕様に項目がある」と「mankenで安全に正規化できる」は別なので、同じ列で表現しない
- 販売系APIは検索対象や価格・在庫が変動するため、個別実例を恒久的な保証として扱わない
- capability表をそのままGoインターフェースへ変換すると、プロバイダ固有の検索条件を失う可能性がある

## 未決事項

- TODO027の完了を妨げる未決事項はない
- 未実装プロバイダは、原則として各実装TODOの調査段階で認証、検索条件、ページング、制限値を再確認する。Google Booksのように既存サンプル依存の項目がある場合は、実装前の再確認事項をbacklogに明記する
- capabilityを将来コード上で公開するかは今回確定せず、複数プロバイダ実装後に利用側の実例をもとに再評価する
