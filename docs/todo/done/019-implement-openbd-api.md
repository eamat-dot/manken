# openBD ISBN参照APIを実装

状態: 完了（2026年8月3日）

## 背景

- 現在の実装はMADBだけをデータ取得元としている
- openBDは認証なしでISBNから書誌情報を取得できる
- openBDの応答は `summary`、`onix`、`hanmoto` に分かれ、同じ概念の値が
  複数箇所に存在する
- 現在の共通モデルは、取得元の値と安全に正規化した値を分けて保持できる

## 目的

- 複数のISBNを指定し、openBDから対応する書誌情報を1回で取得できるようにする
- openBD固有の応答を非公開型で受け取り、`api.Book` へ変換する
- 通常の単体テストと実サービス確認を分離する
- 後続の取得元実装で再利用できるパッケージ構造とテスト方法を確立する

## 非目的

- タイトル、著者名、フリーワードによるopenBD検索
- Google Books、楽天、Yahoo!など他の取得元の実装
- 複数取得元の横断検索、結果の統合、重複排除
- 楽天Booksの検索結果をopenBDで補完する処理
- openBD応答の全項目を `api.Book` へ追加すること
- 在庫、送料、重版予定など販売運用情報の共通モデル化
- キャッシュ、自動リトライ、クライアント側のレート制限

## 前提・制約

- 共通型と共通エラーは `api` パッケージに定義する
- openBD固有の応答型と変換規則を公開APIへ露出させない
- openBDパッケージからMADBパッケージをimportしない
- 取得元の値を推測で補完せず、変換できない値は元値またはRaw responseに残す
- `Sources` は正規化に使用した主要な元値を変更せず保持し、
  Raw response全体は専用メソッドで返す
- 正規化では項目の分解、形式統一、確定済みコードの対応付けだけを行い、
  要約、翻訳、推測による追加、意味を変える置換を行わない
- ISBNは外部サービスへ送信する前に形式とチェックディジットを検証する
- 通常の単体テストから実サービスへ接続しない
- ログ出力、goroutineの開始、自動リトライ、キャッシュを行わない

## リスク・懸念

- 同じ概念が複数セクションに存在し、採用順序を誤ると値の意味が変わる
- ONIXのコード値を不完全に解釈すると、寄与者、日付、価格などを誤分類する
- `summary.volume` はCollection階層の刊行番号を含むため、巻数として利用できない
- 出版社ごとに項目の有無と表記が異なる
- openBDはISBN参照専用であり、単独ではタイトル検索の取得元にならない
- 外部サービスのスキーマと提供状況は将来変更される可能性がある
