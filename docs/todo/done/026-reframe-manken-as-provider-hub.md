# mankenを検索プロバイダのハブとして再整理する

## 背景

- 現状:
  - `manken` は、取得元ごとに異なる書誌情報を共通の `NormalizedBook` へ変換することを中心に設計してきた
  - Raw responseは専用メソッドで利用でき、将来のMCPサーバーも検討対象になっている
  - DMM.com Webサービスの調査により、主要な書誌検索元としては弱くても、電子書籍の商品・販売情報源として有用な取得元があることが分かった
- 課題:
  - 「正確な共通書誌モデルへ変換できるか」を主な評価軸にすると、商品検索、価格、販売URLなど別用途で有用な取得元を過小評価しやすい
  - 将来のMCP / LLM利用では、`NormalizedBook` とRaw responseのどちらか一方ではなく、用途に応じて両方を利用できる方がよい
  - 現行 `docs/concept.md` は正規化を中心とした目的を記載しており、`docs/idea.md` で整理した新しい方向性とずれがある
- 変更が必要な理由:
  - 今後のGoogle Books、楽天Books、楽天Kobo、Yahoo!ショッピング等の調査・実装を、新しい評価軸で一貫して判断できるようにするため

## 目的

- このTODOで達成すること:
  - `manken` の設計上の中心を、正規化だけでなく「複数の書籍・電子書籍・販売系プロバイダへ共通の入口からアクセスするハブ」として整理する
  - `NormalizedBook` とRaw responseを用途に応じて利用する責務分担を明確にする
  - プロバイダを用途別に評価し、書誌検索に弱い取得元も商品・販売情報源として評価できる方針を文書化する
  - DMM.com Webサービスのbacklog上の位置づけを新しい評価軸に合わせる
- 期待する利用者視点の結果:
  - 将来の利用者が、共通化された書誌情報を利用する場合と取得元固有の情報を利用する場合を選べる方向性が分かる
  - MCP / LLM利用でも `NormalizedBook` とRaw responseの双方を利用できることが設計上の候補として明確になる

## 非目的

- 今回は扱わないこと:
  - 公開Go API、型、インターフェースの変更
  - `NormalizedBook`、販売情報、アフィリエイト情報の新しい共通型の設計・実装
  - 複数プロバイダを実際にまとめて検索する横断検索の実装
  - MCPサーバーの実装、MCP SDK選定、ツールSchemaの確定
  - DMM.com Webサービスのプロバイダ実装
- 別Issueや別TODOで扱うこと:
  - プロバイダごとの検索・取得能力を比較するcapability整理
  - Google Books、楽天Books、楽天Kobo、Yahoo!ショッピング等の個別調査・実装
  - 販売情報やアフィリエイト情報の共通モデルが必要かの判断

- 変更してよい範囲:
  - `docs/concept.md`
  - `docs/backlog.md`
  - 必要な場合の `docs/idea.md` の軽微な整合調整

  - Goコードと公開API
  - 現在実装済みの動作を表す `docs/spec.md` を、未実装機能が存在するように書き換えない

- 互換性要件:
  - 現行の `Book`、`NormalizedBook`、`BookSource`、`WithRawResponse` 系メソッドの仕様を変更しない
  - 現在「複数取得元をまたぐ検索・MCPサーバーは未実装」とする仕様と矛盾させない
- パフォーマンス要件:
  - 文書整理のみのため該当なし

## 想定ユースケース

- 入力:
  - 書誌情報、商品情報、販売情報を提供する複数の外部サービス
- 実行:
  - 利用者は用途に合うプロバイダを選び、共通化できる情報は `NormalizedBook`、取得元固有の詳細はRaw responseとして利用する
  - 将来のMCP / LLM利用では、`NormalizedBook`、Raw response、または両方を利用する
- 出力:
  - 各プロバイダの特性を保ちつつ、共通処理が必要な箇所では正規化済み情報を利用できる
- 失敗時の扱い:
  - 取得元にない情報や安全に変換できない情報は推測で補完せず、正規化項目を空にするかRaw responseで確認する既存方針を維持する
